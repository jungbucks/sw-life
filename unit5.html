5-1 스타트업 — 불편이 가치가 되는 순간 💡

스타트업 = 세상의 불편을 소프트웨어로 풀어 새로운 가치를 만드는 작은 팀.

거창한 발명이 아니다. 성공한 소프트웨어 스타트업들의 출발점은 전부 "이거 왜 이렇게 불편하지?"였다:

🍗

음식 배달 중개

불편: 전단지 뒤져 전화 주문, 메뉴판은 어디에? → SW: 한 앱에서 검색·주문·결제

💸

간편 송금

불편: 공인인증서와 보안카드의 미로 → SW: 몇 번의 터치로 송금 끝

📦

동네 중고 거래

불편: 낯선 사람과의 거래 불신 → SW: 동네 인증·매너 평가로 신뢰 장치

공통 패턴내용
① 오래된 불편누구나 겪지만 "원래 그런 것"이라 여기던 것
② SW의 강점 결합중개·자동화·신뢰 장치 — 1단원 "융합의 공식"과 같은 구조!
③ 새 가치시간 절약, 새 일자리, 새로운 연결

5-2 사용자 요구 분석 — 아이디어보다 사람 먼저 🎤

스타트업 프로젝트의 순서: 불편 발견 → 요구 분석 → 아이디어 → 최소 기능 제작 → 검증. 두 번째 단계가 승부처다.

불편을 겪는 진짜 사람을 인터뷰하자. 네 가지만 물으면 된다:

인터뷰 질문알아내는 것
① 누가 겪는 불편인가요?타깃 사용자
② 언제, 어디서 겪나요?사용 상황(컨텍스트)
③ 왜 불편한가요? 얼마나 자주?문제의 크기 (가끔 겪는 사소함이면 재검토)
④ 지금은 어떻게 버티고 있나요?경쟁 상대 = 현재의 임시방편
🚨 오개념 주의보 — 내가 만들고 싶은 것 ≠ 사용자가 필요한 것 요구 분석 없이 만든 소프트웨어가 스타트업 실패 원인 1순위다. 멋진 기능을 상상하기 전에, 불편을 겪는 사람의 입에서 나온 말을 먼저 모아라 — 그것이 요구(needs)다.

5-3 아이디어 캔버스 — 한 장으로 설계하기 🗺️

요구를 확인했다면, 팀이 협력해서 한 장짜리 설계도를 채운다.

💡 왜 기능을 3개로 제한하나 — MVP 전부 만들기 전에 핵심만 담은 최소 기능 제품(MVP)으로 사용자 반응부터 검증한다. 기능 10개짜리 미완성보다 기능 3개짜리 완성이 배우는 게 많다 — 실제 스타트업의 철칙이다.

실습 AI와 첫 시제품 만들기 🌱

아이디어 캔버스에서 핵심 기능 하나를 골라, 사람이 직접 써 볼 수 있는 작은 시제품으로 만들어 보자.

자연어로 원하는 프로그램을 설명하고 AI와 대화하며 만들어 가는 방식을 흔히 바이브 코딩이라고 부른다. 이 수업에서는 생성된 결과를 직접 확인하고, 왜 고쳤는지 설명하는 것까지 연습한다. 화면이 예쁘게 나와도 기능이 정확하다는 뜻은 아니다.

1. 도구 고르기 · 하나면 충분해

Canva AI · Canva Code

말로 설명해 상호작용하는 콘텐츠를 만드는 기능. 퀴즈나 간단한 계산기를 만드는 활동에 활용해 보자.

Canva Code 공식 안내 ↗

Gemini Canvas

앱과 코드를 만들고 미리 보며 수정하는 작업 공간. 입력값에 따라 결과가 바뀌는 작은 도구를 만들어 보자.

Gemini Canvas 공식 안내 ↗

ChatGPT Sites

대화로 웹사이트와 간단한 앱을 만들고 미리 보는 기능. 우리 팀 아이디어를 작동하는 웹 화면으로 표현해 보자.

ChatGPT Sites 공식 안내 ↗

도구 안내 확인: 2026. 9. 10. 사용 가능 여부는 계정·요금제·학교 설정에 따라 다르며, Sites는 이용 가능한 요금제나 작업 공간이 필요하다. 교사가 사용 조건을 확인한 도구로 진행하자. 외부 도구는 인터넷이 필요하지만, 아래 요청문·검증 기록 활동은 오프라인에서도 할 수 있다.

계정이 없어도 같은 과정을 연습할 수 있어요청문을 작성하고 종이에 입력 화면과 결과 화면을 그린 뒤, 짝이 사용자인 것처럼 시험해 보자. 실제 프로그램을 실행한 결과와 종이 설계로 예상한 결과는 기록에서 구분한다.

2. 요청하기 · 입력과 결과를 구체적으로

“예산 계산기 만들어 줘”에 누가 쓰는지, 입력값, 계산 규칙, 예외 처리를 더하면 확인할 기준도 생긴다.

요청문 예시 · 동아리 행사 예산 계산기동아리 학생이 쓸 예산 계산기를 만들어 줘. 참가 인원은 1 이상의 정수, 1인당 비용은 0 이상의 정수(원)로 입력받아 둘을 곱한 총비용을 보여 줘. 빈칸·음수·소수는 계산하지 말고 이유를 안내해 줘. 이름과 연락처는 받지 말고, 휴대폰에서도 입력란과 계산 버튼을 읽기 쉽게 만들어 줘.

3. 확인하기 · AI의 ‘완료’ 대신 직접 시험

먼저 예상 결과를 적고 실제 결과와 비교하자. 다음은 위 예산 계산기의 기준이다. 우리 팀 프로그램에는 그 목적에 맞는 기준을 정한다.

예산 계산기의 테스트 예시
입력 (인원 / 비용)예상 결과
3 / 2,000총비용 6,000원 (숫자 입력은 2000)
3 / 0총비용 0원 · 무료 행사도 가능
0 / 2,000 또는 빈칸입력 안내 표시, 계산하지 않음
−1 / 2,000 또는 1.5 / 2,000인원은 1 이상의 정수라는 안내
100 / 100,00010,000,000원 · 작은 화면에서도 읽을 수 있음
계정 없이 오류 찾기 · 0명을 넣었는데 0원이 나왔다면?
계산식만 보면 0원이지만, 요청문은 인원을 1 이상으로 정했다. 따라서 입력 안내를 보여 주어야 한다. 수정 요청 예: “인원이 0일 때 계산되는 문제가 있어. 1 이상의 정수인지 먼저 확인하고, 올바르지 않으면 기존 계산 결과도 지워 줘.” 수정한 뒤 0명과 정상 입력 3명을 모두 다시 시험하자.

4. 고치기 · 짝의 피드백으로 한 번 더

짝에게 설명 없이 써 보게 하고 막힌 곳을 관찰하자. 발견한 문제를 AI에 구체적으로 설명해 수정한 뒤, 문제가 생겼던 입력과 정상 입력을 다시 확인한다.

공개하기 전, 연습용 자료로 확인하자실명·연락처·실제 성적 대신 가상의 데이터를 사용하자. 이 활동은 공개 배포 없이 미리보기나 종이 설계로 마쳐도 된다. 가져온 이미지·자료의 출처와 사용 조건도 확인한다.

평가의 기준: 도구의 종류나 화면의 화려함보다 문제를 얼마나 구체적으로 설명했는지, 어떤 오류를 찾았는지, 근거를 들어 수정했는지를 살핀다. 아래 3관점 평가에 이 기록을 활용하자.

5-4 세 개의 거울 — 사회적·기능적·윤리적 평가 🪞

만들었다고 끝이 아니다. 개발한 소프트웨어를 세 관점의 거울에 비춰 보자.

💡 가치의 완성은 평가다 3단원의 데이터 윤리, 4단원의 "모델의 한계"와 같은 정신이다 — 내가 만든 것이 세상에 낳을 결과까지 살피는 것이 소프트웨어로 가치를 만드는 사람의 마지막 책임이다.
